Findings

[80] 1. HookFactory.deployHook grants instant, unbounded, timelock-unreachable damage on owner compromise

HookFactory.deployHook · Confidence: 80 · Severity: High · Origin: [phase1: access-control]

Description
deployHook is onlyOwner, carries no timelock delay, and accepts arbitrary attacker-supplied
initCode — unlike every other owner-reachable lever (all capped and/or timelocked), a malicious
hook it deploys can set permission bits SimHook deliberately never sets (e.g.
afterRemoveLiquidityReturnDelta) and divert funds directly; the only content check (a reverse
governance() pointer read) is trivially satisfied by the attacker's own constructor, and once
verified, isCanonicalHook() — the documented authoritative integrator check — returns true
before any ≥24h timelock notice period could matter.

Proof of Concept
Compromise owner → craft EvilHook whose constructor stores the real governance address (the
only check deployHook performs) but whose swap/liquidity callbacks are fully attacker-authored
→ deployHook succeeds in one tx (isVerifiedHook=true, subscribed) → configurePool/pool-init
(also instant, no timelock) puts a live pool behind it in the same or next tx → LPs/swappers
trusting isCanonicalHook()==true interact and lose funds → by the time a timelock rotation could
respond (≥24h), funds already in motion are gone; KI-5 (no kill switch) and
removeSubscriber's deposit-only quarantine don't reach funds already interacting with the
malicious hook.

Fix

- function deployHook(bytes calldata initCode, bytes32 salt, address expectedAddress)
-     external
-     onlyOwner
+ function deployHook(bytes calldata initCode, bytes32 salt, address expectedAddress)
+     external
+     onlyTimelockScheduled  // or: require a mandatory cooling-off window between
+                            // isVerifiedHook being set and pool-init eligibility

At minimum, document this asymmetry explicitly in docs/known-issues.md — it is not currently
covered, unlike every other owner-lever's blast radius.

[82] 2. JIT lock's fee-only "poke" path is unguarded — defeats the lock's entire documented anti-sandwich purpose

SimHook._beforeRemoveLiquidity · Confidence: 82 · Severity: High · Origin: [phase2: pashov agent 11 — trust-gap]

Description
The JIT lock — the sole gate on liquidity removal — only checks params.liquidityDelta < 0;
a fee-only "poke" (liquidityDelta == 0, standard Uniswap v3/v4 mechanic that settles accrued
fees without touching principal) routes past the check entirely and is never gated, letting a
JIT sandwicher extract the trade's fee payoff — the entire economic point of the sandwich —
immediately, with zero holding-period risk, while their untouched principal keeps earning
further yield.

Proof of Concept
Attacker adds narrow, concentrated liquidity immediately ahead of a large incoming trade →
_afterAddLiquidity stamps lastAddedLiquidityBlock → the large trade executes against the
attacker's concentrated range, generating an outsized LP-fee share → attacker calls
modifyLiquidity(liquidityDelta=0, same position key) → _beforeRemoveLiquidity's
if (params.liquidityDelta < 0) is false → function returns immediately, no lock check runs →
v4-core settles the accrued fee to the attacker in the same/next transaction, fully inside the
configured jitLockBlocks window. Confirmed against the repo's own
test/feature/JitLock.t.sol::test_poke_doesNotResetClock, which exercises exactly this call
shape and asserts it does not revert — the test checks only that the clock isn't reset, never
that the fee payout is blocked.

Fix

- if (params.liquidityDelta < 0) {
+ if (params.liquidityDelta <= 0) {
      PoolId poolId = key.toId();
      uint48 lockBlocks = poolConfig[poolId].jitLockBlocks;
      ...

(Alternative: track a separate "fees claimable" checkpoint distinct from principal-removal
eligibility, if blocking routine fee compounding for genuine LPs for the whole lock window is
judged too costly.)

[80] 3. Zero-liquidity gap-walk lets a positioned LP manufacture fee-accumulator saturation — closes a client-flagged open lead

SimHook._afterSwap / calculateDynamicFee · Confidence: 80 · Severity: High ·
Origin: [phase2: pashov agents 3 & 12 (economic-security, flow-gap) — independently converged;
corroborated by agents 4 & 5 as unclosed leads]

Description
A dominant/concentrated LP can walk price through a zero-liquidity gap (a property of any
concentrated-liquidity pool) for near-zero real cost — v4-core consumes no input while
liquidity==0. The resulting swapDelta is nonzero, so _afterSwap's exact-zero guard doesn't
fire, and the full traversal is booked as impact, saturating cumPriceImpact. Every subsequent
organic swap, either direction, then clamps to maxFee — an order-of-magnitude-plus overcharge
versus what its real (small) impact would justify — and the attacker, as dominant in-range LP,
collects the LP share of that inflated fee. docs/known-issues.md KI-6 explicitly leaves this
"dominant-LP recapture" variant as "an open lead, not closed here"; this finding closes it with a
concrete, cheap trigger at ordinary (non-100%) maxFee settings.

Proof of Concept
At maxFee=30,000 pips (3%), shipped-default weights kPips=2e6/cPips=1e6: one saturating
swap pushes |cum|≈1,000,000, clearing both of KI-11's own derived clamp thresholds (15,000
imbalancing / 60,000 healing) by 17–67×. A subsequent organic swap with genuinely small impact
(~100 pips) computes dynamicImpactFee≈2,000,100 pips (200%), clamped to the 3% ceiling.

Fix
Distinguish "impact through real liquidity" from "impact through an empty gap" when booking
cumPriceImpact (e.g. measure impact only over the sub-path where nonzero liquidity was actually
consumed), or dampen the accumulator's sensitivity to near-zero-liquidity traversals. At minimum,
elevate KI-6's open lead to a quantified, monitored risk with explicit maxFee-sizing guidance
for deployers.

[70] 4. SwapSimulator's fee-free replay walks empty tick-bitmap words the real swap never visits — refutes part of KI-2's stated reasoning

SwapSimulator._simulate · Confidence: 70 · Severity: Medium · Origin: [phase1: dos]

Description
KI-2 accepts the simulator's double tick-walk on the premise "vanilla v4 walks the same ticks for
the same order" — true outside KI-1's overquote window, false inside it: a fee-free simulation of
an exact-input order sized at the real book's capacity exhausts the liquid band using less
notional than the real (fee-charged) swap, so it exits into empty tick-space and scans additional
cold getTickBitmap words the real swap never pays for.

Proof of Concept
At tickSpacing=1 with a loose price limit, up to ~3,466 extra words toward MIN_TICK ≈ 13.9M
gas the real swap/vanilla-v4 never incurs — potentially pushing total tx gas toward block limits
for an order that would otherwise execute cheaply.

Fix
Short-circuit _simulate once it detects zero-liquidity consumption outside the real book and
treat the remainder as saturated (100%) impact directly, matching the maxFee outcome KI-1
already assigns to this order class.

[70] 5. MAX_JIT_LOCK_BLOCKS/jitLockBlocks calibrated for 12s blocks, shrinks ~6× on 2s-block L2s

SimHook.sol (MAX_JIT_LOCK_BLOCKS, _beforeRemoveLiquidity, _afterAddLiquidity) ·
Confidence: 70 · Severity: Medium · Origin: [phase1: chain-specific]

Description
The JIT lock is block.number-denominated, and both the ceiling's NatSpec and deployer guidance
reason exclusively in mainnet-block terms ("≈7 days of 12s blocks"). On Base/Optimism (~2s
blocks), following that guidance literally yields a wall-clock lock ~6× shorter than intended,
narrowing the deterrent window against JIT liquidity sniping — compounding with Finding 2 above on
any L2 deployment, since the poke bypass makes the lock's actual protection even thinner than the
timing miscalibration alone suggests.

Fix
Switch the JIT-lock clock to block.timestamp (as the ramp/decay clocks already use), or require
an explicit per-chain block-time parameter when deriving jitLockBlocks.

[65] 6. setProtocolFeeBps broadcast loop has adequate but not generous gas margin, no chunking fallback

AscntGovernance.setProtocolFeeBps · Confidence: 65 · Severity: Low · Origin: [phase1: dos]

Description
Worst case ≈14.2M gas fits current mainnet block limits but has no chunking fallback; on L2s with
lower per-block gas limits this could exceed the limit, blocking setProtocolFeeBps until
subscribers are pruned one at a time. Requires 256 adversarial subscribers (compromised owner
precondition) — not externally triggerable today.

Fix
Add a paginated broadcast variant (caller-supplied [start, end) slice), or document a minimum
acceptable block gas limit per deployment target.

[60] 7. KI-8's stated "~13 blocks of exposure" mitigation narrows proportionally on faster L2s

SimHook._beforeSwap (ramp-anchor settle) · Confidence: 60 · Severity: Low ·
Origin: [phase1: chain-specific]

Description
